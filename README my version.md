# Wazuh-Lab-115-PowerShell-Alert-Tuning
## Overview
Wazuh uses rules to analyze collected security events and generate alerts when specific conditions match. Each rule can define a detection condition, alert description, severity level, and other matching criteria.

In a SOC environment, some rules may repeatedly alert on legitimate activity. For example, expected authentication failures during routine testing or frequent system events may generate a large number of alerts. When these alerts are not investigated carefully, they can increase alert fatigue and distract analysts from more important events.

Rule tuning means refining detection logic to reduce unnecessary alerts without losing visibility into meaningful security activity.
### Why do noisy alerts occur?
Common causes include:
- A rule matches activity that is normal in the monitored environment.
- A rule uses conditions that are too broad.
- Repeated events trigger alerts without sufficient context.
- An expected administrative or application behavior resembles suspicious activity.
- The rule's severity or detection logic does not adequately reflect the observed risk.
A high alert count does not automatically mean a rule is poorly designed. The events must be investigated before changing detection behavior.
### How should an analyst tune a rule?
A safe tuning process follows these principles:
1. Investigate first: Review the alert, underlying event, rule ID, severity, timestamp, agent, and related activity.
2. Understand the original rule: Determine which conditions cause it to match and why the observed events trigger it.
3. Choose a narrow adjustment: Prefer a specific exception or refined condition over disabling a rule entirely.
4. Preserve detection coverage: Ensure the adjustment does not suppress unrelated or genuinely suspicious events.
5. Validate the change: Test the rule configuration and compare the behavior before and after tuning.
6. Document the result: Record the reason for tuning, the change made, test evidence, and any remaining limitations.


This lab investigates repetitive Wazuh alerts generated when PowerShell creates temporary script files under the Windows `SystemTemp` directory. The objective is to understand the original detection rule, examine the associated Sysmon evidence, and develop a narrowly scoped custom rule to reduce repetitive alerts without suppressing unrelated file-creation activity.

The investigation focuses on Wazuh rule `92205`, Sysmon Event ID 11, and custom rule development in `local_rules.xml`.

## Lab Objectives

- Investigate repetitive Wazuh alerts associated with PowerShell file-creation activity recorded by Sysmon Event ID 11.
- Examine the original Wazuh rule `92205` to understand its matching conditions, severity level, and detection scope.
- Analyze alert fields, including the PowerShell executable path, target filename, user context, and endpoint details.
- Determine whether repeated alerts share a consistent pattern without assuming that the activity is benign solely from the filename or process.
- Develop a narrowly scoped local Wazuh rule to suppress the specific script-policy test file pattern observed during the investigation.
- Validate custom rule syntax and hierarchy to prevent XML configuration errors and unintended rule nesting.
- Use `wazuh-logtest` to verify whether the proposed rule matches representative Sysmon event data.
- Confirm that tuning does not unintentionally suppress unrelated PowerShell file-creation events.
- Document validation results, unresolved issues, and deployment limitations before applying changes to the running Wazuh manager.

## Lab Scenario

A SOC analyst notices repeated Wazuh alerts generated by PowerShell-related file-creation activity on a monitored Windows endpoint. The alerts are associated with Sysmon Event ID 11 and trigger rule `92205`, which assigns a high severity level to matching file-creation events involving specific Windows directory paths.

Initial investigation reveals that the events involve PowerShell running from its standard Windows executable path and creating files named `__PSScriptPolicyTest_*.ps1` under `C:\Windows\SystemTemp\`. The events appear repeatedly under the `NT AUTHORITY\SYSTEM` account, creating alert noise that may make it harder to identify more significant activity.

The analyst must determine whether the repeated events share a consistent pattern, examine the original detection rule, and assess whether a narrowly scoped exception is appropriate. The goal is to reduce unnecessary alerts without broadly suppressing PowerShell file-creation activity or weakening detection coverage.

### Investigation Tasks

- Review the original rule `92205` and identify the conditions responsible for generating the alerts.
- Examine the available event fields to establish the process, target file path, user context, and affected endpoint.
- Create a custom local rule that targets only the observed script-policy test file pattern.
- Validate the XML structure and test the proposed rule using `wazuh-logtest`.
- Check that unrelated PowerShell file-creation events can still trigger the original detection.

The investigation is not considered complete until the custom rule's matching behavior is verified. Repeated filenames and consistent event patterns alone do not prove that the activity is harmless, and changes should not be deployed to the running manager until validation is successful.

## Detection Rule Analysis

The original rule was located in:

`/var/ossec/ruleset/rules/0830-sysmon_id_11.xml`

Its relevant configuration was:

```xml
<rule id="92205" level="9">
  <if_sid>92203</if_sid>
  <field name="win.eventdata.targetFilename" type="pcre2">(?i)Windows\\\\(system|syswow64|temp)</field>
  <options>no_full_log</options>
  <description>Powershell process created an executable file in Windows root folder</description>
  <mitre>
    <id>T1105</id>
  </mitre>
</rule>
```

The rule matches a parent rule and a target filename containing one of the specified Windows directory patterns. The broad directory matching helps explain why the observed `SystemTemp` paths triggered the rule.

The MITRE ATT&CK mapping is part of the original rule configuration. It does not, by itself, establish that ingress tool transfer occurred during these events.

## Investigation Workflow

1. Locate rule `92205` in the installed Wazuh ruleset.
2. Examine the corresponding alert records in `alerts.json`.
3. Identify recurring process, user, directory, and filename characteristics.
4. Back up `local_rules.xml` before modifying it.
5. Develop a custom rule using ID `100502`.
6. Validate the XML configuration with `xmllint`.
7. Run `wazuh-logtest` to investigate rule matching.
8. Correct the nested XML rule structure discovered during troubleshooting.
9. Revalidate the configuration and continue testing before applying the change.

## Key Findings

- Rule `92205` generated repeated level-9 alerts for Sysmon Event ID 11.
- The observed process was Windows PowerShell.
- The recurring target path was `C:\Windows\SystemTemp`.
- The observed filenames followed the `__PSScriptPolicyTest_*.ps1` pattern.
- The events identified `NT AUTHORITY\SYSTEM` as the user.
- The original rule's directory-matching condition was broader than the specific filename pattern observed.
- An incorrectly nested custom rule caused `wazuh-logtest` to fail during initialization.
- XML validation subsequently completed without reporting syntax errors.
- Successful custom-rule matching and operational deployment remain unconfirmed.

## Troubleshooting Lessons

### Nested rule structure

Wazuh rules must be separate sibling elements within their enclosing group. A `<rule>` element cannot contain another `<rule>` element.

### XML validation versus rule validation

A successful `xmllint` run establishes XML syntax validity. It does not establish that Wazuh accepts every rule option or that a rule matches the intended event.

### Rule-matching verification

A custom rule must be tested against representative telemetry. The decoded fields, parent-rule relationship, and final matched rule should be inspected before applying a tuning change.

### Narrowly scoped tuning

Suppressing every alert from PowerShell or disabling rule `92205` globally could hide legitimate suspicious activity. Any exception should be restricted to a well-understood pattern and supported by additional validation.
